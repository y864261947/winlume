01 · 当前整体结构

Reizo 是一个以 Next.js 为主体的全栈应用。用户界面和大部分业务后端位于同一仓库、同一应用中，按业务模块组织；不是已经全面拆分的微服务系统。

03 · 用户、工作区和 Key

用户 → 加入工作区
工作区 → 对应一个 new-api 后端账号
工作区 → 系统维护的内部工作台 Key
工作区 → 用户创建或纳管的外部 API Key

三种凭证不能混为一谈

凭证用途用户如何参与
登录会话证明用户已登录 Reizo。正常登录即可。
工作区管理凭证 PATReizo 后端管理网关中的 Key、读取余额。无需操作，不应暴露给用户。
模型调用 Key实际请求模型，包含内部工作台 Key 和外部 API Key。工作台自动使用；外部开发按需创建。
用户不需要手动创建 Key 才能使用工作台。当前开户流程会创建内部凭证，调用时检查工作区归属和有效状态。这不等于无条件访问所有模型：仍受模型支持、工作区权限、路由可用性及可用资金约束。

06 · 计费现状与尚未启用的部分

当前已实现

  • 钱包区分会员额度与充值余额的展示。
  • 充值余额读取当前网关的数据。
  • 模型定价管理连接 new-api 定价体系。
  • 会员额度有数据类型与百分比计算方法。

尚未启用

  • 会员额度池及实际扣减。
  • 用户选择的余额兜底机制。
  • Reizo 自有统一结算账本。
  • 新结算流程中的预留、结算、退款及防重复扣费。

当前不能视为 Reizo 已独立掌握完整计费。用户操作入口逐步集中到 Reizo，底层扣费仍依赖 new-api。

已讨论的产品方向：会员额度按周期展示剩余百分比；充值余额按模型用量计价；优先使用额度，余额兜底需用户选择。具体套餐额度、换算规则和周期细节仍需确定。

07 · 目标架构与迁移顺序

后续由 codex-proxy 替代 new-api，专注模型调用与后台管理。用户可见的功能统一保留在 Reizo。

Reizo：用户与商业业务codex-proxy：模型执行基础设施
用户、工作区、会员、充值上游账号、渠道、凭证
用户模型权限和售价模型路由、协议转换
额度、余额、消费账本实际调用、用量采集
用户 Key、日志与账单界面重试、限流、健康检查、管理员诊断

建议实施顺序

  1. 统一网关协议：明确模型调用、目录、Key、用量和错误格式，约定调用与结算如何衔接。
  2. 建立 Reizo 结算账本：定义每次请求的预留、结算、退款和幂等规则。
  3. 统一模型目录：关联门户展示、工作台可选模型、用户权限和模型定价。
  4. 迁移会话存储：为多实例部署和并发访问准备。
  5. 验证后切换网关：确认 codex-proxy 支持现有对话、图片等调用协议，再逐步替换 new-api。
codex-proxy 尚未正式接入；不能仅替换网关地址就认定迁移完成。必须验证协议兼容、凭证迁移、权限、用量与结算链路。

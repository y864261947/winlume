REIZO / OWNER A / PERSONAL + PLATFORM

个人版目标执行规划

负责人 A 的目标不是继续扩展门户页面，而是让一个新用户可以从发现能力开始，真实完成一次调用、看到用量、管理 Key，并在异常时得到可执行的反馈。A 同时负责共享平台底座，避免登录、账户、调用、计费与发布成为无人负责的横向风险。

建议负责人：开发者 A计划周期：T0 → T0+6 周主线：个人用户闭环共享职责：new-api / 部署 / 发布验收最终产出：可公开使用的个人版 1.0

一、职责边界

A 对个人体验及所有影响个人用户的共享平台能力负责；企业线索、案例和方案内容由 B 负责。A 不等待企业页面完成，但要向 B 提供可安全复用的账户、团队、通知和发布能力。

PRIMARY

个人版产品体验

主页、应用工具、模型目录、文档、公开计费、账户中心、工作台的关键路径和统一体验。

SHARED PLATFORM

账户与调用底座

注册登录、会话、API Key、团队 Token、new-api 调用、用量读取、余额与错误处理。

RELEASE

发布安全

生产配置、自动部署、健康检查、日志、备份、回滚演练和个人版冒烟测试。

三、六周执行拆分

每周结束必须由 A 给出可演示账号、测试步骤和未关闭问题。未经测试记录确认的功能不进入“完成”。

T0+1 周

闭环基线与测试账户

建立个人版发布测试清单，先跑通现有能力，暴露真实阻断项。

  • 创建至少 3 类测试账号：新用户、普通用户、团队成员。
  • 从主页、目录、工作台、账户逐条走通关键路径并记录截图/日志。
  • 整理 P0/P1 问题：不能注册/登录、不能调用、Key 失效、数据错账、页面阻断。
  • 明确生产模型白名单与每个模型/应用的可用状态。
T0+2 周

调用、Key 与用量一致性

让 new-api 的真实能力在 Reizo 内有一致、可解释的用户体验。

  • 验证注册后 new-api 用户、Studio Token、虚拟 API Key 的创建与生命周期。
  • 验证 /v1/models、聊天或生成接口转发，完成 Key 创建→调用→撤销回归。
  • 核对工作台记录、账户用量、余额显示与 new-api 后台的单位/时间/用户归属。
  • 给模型目录和公开计费页增加真实数据或明确“参考展示”边界。
T0+3 周

失败体验、权限与安全

将正常路径之外的风险收口，避免正式上线时由客服解释系统错误。

  • 完成：未登录、无权限、余额不足、额度耗尽、无模型、上游 4xx/5xx、超时、网络断开。
  • 审查浏览器、服务日志、错误边界中是否出现密码、Token、完整 Key、用户敏感信息。
  • 验证个人/团队边界：用户不能读取或撤销其他用户/团队的资源。
  • 完成移动端关键路径回归：主页→工作台、账户→Key、目录→详情。
T0+4 周

个人版灰度

邀请 10–15 位真实测试者，以任务成功而不是“看起来不错”作为通过标准。

  • 每位测试者完成一次工作台任务和一次目录/API 任务。
  • 记录首个任务完成率、模型调用成功率、首次错误位置、客服问题。
  • 修复所有 P0/P1；P2 明确是否可延后及临时说明。
  • 与 B 一起确认企业 CTA 不会破坏个人用户导航和账号状态。
T0+5 周

发布演练

进行一次上线、回滚、恢复和冒烟测试的完整演练。

  • 验证 GitHub Actions 部署、服务健康检查、数据库迁移和日志位置。
  • 完成数据库备份与恢复演练，记录耗时与操作人。
  • 回滚上一个稳定包并再次完成注册、调用、Key、用量四项冒烟测试。
T0+6 周

个人版正式放量

内部 → 受邀用户 → 小流量公开 → 全量；每一阶段观察后再放大。

  • 监控登录成功率、调用成功率、P95 延迟、异常用量、客服量。
  • 满足回滚阈值时立即暂停放量并通知 B，防止企业线索导入故障版本。
  • 发布后 7 天每日复盘；第 30 天整理留存、调用、Key 和付费/咨询转化数据。

四、A 的验收门槛

必须全部通过

  • 新账号可注册、登录、退出与重新登录。
  • 一条文本和一条图像/非文本路径真实返回结果。
  • Key 创建、调用、撤销完整成功。
  • 用量与余额变化可解释且用户归属正确。
  • 未登录、余额不足、上游失败不出现空白页或无解释错误。
  • 生产部署、健康检查、备份、回滚演练均有记录。
禁止以“已上线”换取的风险
不在未验证实际扣费前宣传准确价格；不在无法撤销 Key 或权限隔离不明确时开放 API；不在没有故障负责人和回滚能力时扩大流量；不将测试模型或虚构成功案例当作已稳定服务。
